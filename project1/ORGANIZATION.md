# Project1 조직 구조와 운영 방식

## 1. 조직도

```
대표 (사람)  ── 방향, 예산, 승인, 계정/본인인증/결제
   │
COO  p1-coo (fable)  ── 우선순위, 배분, 취합, 대표 보고
   │
   ├─ 공통 지원팀 (모든 사업체가 공유)
   │    CTO p1-cto (opus)        설계·구현·코드 품질
   │    리서처 p1-researcher     시장·경쟁·기술 조사
   │    마케터 p1-marketer       포지셔닝·콘텐츠
   │    영업 p1-sales            견적·문의 응대·상품 문구
   │    QA/감사 p1-qa            검증, 법규·개인정보·표시광고
   │    재무 p1-cfo (haiku)      장부, 수수료, 손익
   │    운영보조 p1-ops (haiku)  정리·요약·포맷
   │
   └─ 사업체 (project1/company-*/)  ← 지원팀이 필요할 때 투입됨
```

사업체에 상주 인력은 없다. 사업체는 폴더(`README.md`, `STATE.md`)이고, 지원팀 에이전트가 작업할 때마다 그 폴더를 읽고 갱신한다. 인원이 늘어 보이는 효과 없이 사용량만 늘리는 상주 에이전트는 두지 않는다.

## 2. 일이 흐르는 방식

1. 대표가 목표를 준다. (예: "이번 주 1번 사업체 첫 의뢰 받기")
2. COO가 `companies.md`와 해당 `STATE.md`를 읽고 작업으로 쪼개 지원팀에 배분한다.
3. 지원팀이 산출물을 해당 사업체 폴더에 만든다.
4. QA가 검증한다. 외부에 나가는 모든 것은 QA를 거친다.
5. COO가 취합해 대표에게 요약 보고하고, 승인이 필요한 항목을 올린다.
6. `STATE.md` 갱신, 결정과 결과는 `project1/log/`에 날짜별로 기록.

## 3. 결정 권한

| 구분 | 예시 | 누가 결정 |
|---|---|---|
| 자율 | 초안 작성, 조사, 정리, 내부 문서, 샘플 제작 | 에이전트 |
| 승인 필요 | 외부 발송, 고객 답변 전송, 가격 확정, 게시, 배포 | 대표 |
| 대표 전용 | 계정 개설·본인인증, 결제, 계약, 사업자등록, 세무, 실투자 | 대표 (에이전트는 준비만) |
| 금지 | 가짜 후기·실적, 타인 명의 사칭, 계정 공유 요청, 종목 추천 유료화 | 아무도 하지 않음 |

## 4. 소통과 기억

- 에이전트끼리는 대화로 정보를 넘기지 않고 파일로 넘긴다.
- 새 세션은 `project1/README.md`, `companies.md`, 해당 사업체 `STATE.md`만 읽으면 이어갈 수 있어야 한다.
- 에이전트는 작업 종료 전 `STATE.md`의 "다음 할 일"을 갱신한다.

## 5. 운영 리듬

- 매일: COO가 활성 사업체 `STATE.md`를 보고 오늘의 3가지를 대표에게 제안.
- 매주: 사업체별 매출·비용(`finance/ledger.csv`)과 성과 점검, 활성화/중단 결정.
- 활성 사업체는 동시에 2~3개. 첫 매출이 나면 다음을 연다. 4주 안에 첫 문의도 없으면 중단하거나 접근을 바꾼다.

## 6. 비용(사용량) 관리

- 판단이 필요한 일은 fable/opus, 조사·작성은 sonnet, 반복·정리는 haiku.
- 한 번에 병렬로 돌리는 에이전트는 최소화하고 산출물은 파일로 남겨 재작업을 막는다.
- 사용량이 부족하면 1차 사업체에만 집중한다.

## 7. 성과 지표

- 사업체별: 문의 수, 수주 수, 매출, 수수료 차감 후 순수익, 납품 소요시간.
- 회사 전체: 월 순수익, 활성 사업체 수, 대표가 쓴 시간(줄이는 것이 목표).

## 8. 한계와 규칙

- 제가 만든 계획과 가격은 가정이다. 첫 의뢰 결과를 보고 고친다.
- 사람이 해야 하는 일(본인인증, 결제 등)이 자동화의 병목이다. 이를 모아서 한 번에 처리하도록 목록을 만든다.
- 법규 사항(사업자등록, 통신판매업, 개인정보, 투자 자문)은 QA가 점검하고 대표가 최종 확인한다.
